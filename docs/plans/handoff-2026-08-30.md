## The state of the model

**`component/1.0` is the default and is unchanged.** Projections are
byte-identical to what they were before FU-47 landed —
sha256 `c3812c8cae30c609b41243f3a26dcc49450c8b03993604ffb6129470037a7412` over
all 3080 rows of the pinned capture. If that moves, something is wrong.

**`component/1.1-price` and `component/1.1-position` are registered and are not
the default.** They differ in exactly one knob — whether xG and xA shrink toward
a price-conditioned prior or a position-only one — and a test asserts that is
the only difference, so any gap between them is attributable to price
conditioning and nothing else.

**The principle is fixed; the parameters are not.** A rate of 270 per 90 from one
minute cannot enter a projection at face value, and that claim needs no
evaluation. Every `M` behind it, on the other hand, is *chosen*: rate-shrinkage.md
§9.2 files them all under "must be measured", §5 calls its own figures
"demonstration parameters, not proposed values", and §4.3 measured that they
cannot be estimated from one gameweek of data. Do not quote 1.1 as better or
worse than 1.0 until the evaluation below has run.

## What is waiting on GW2 settling

At the last sync GW2 was `is_current`, `finished=False`, `data_checked=False`.
Nothing below can run until it settles.

**The sequence, in order — the first two steps are prerequisites, not
formalities:**

1. **`fpl plan evaluate --event 2`, unpinned.** This is what populates
   `~/.fpl-cli/events/2-live.json` with a settled envelope. A pinned run cannot
   do it: FU-43's gate refuses to fetch, so pinning first fails rather than
   silently using a provisional payload.
2. **Copy that file to `~/fpl-pinned/` and `chmod 444`.** Event-live is still not
   part of the capture format (FU-40's own gap block, and FU-43's), so this is
   the only way to pin the third input. Read-only for the same reason the other
   two are: an unpinned run elsewhere would otherwise rewrite it.
3. **The leak-free evaluation**, pinned to all three files and cited per FU-40 —
   both captures *and* the model version, which that entry now requires.

**One evaluation settles three separate questions**, which is worth saying
plainly because it is easy to run it thinking about only one:

- **1.0 versus 1.1** — whether shrinking the rates helps at all.
- **price versus position** — the reason both 1.1 variants exist. The evidence
  for price conditioning is Spearman 0.458 from a single gameweek, thinner than
  the plan's other measurements.
- **component versus naive** — the original benchmark from projections-v1.md
  Decision 6, never yet run leak-free. If the component model loses to the flat
  baseline, the survey's rule applies: fix the minutes model before adding
  complexity.

`plan evaluate --model` takes all of them in one invocation, which is the whole
point of the registry: two runs diffed by hand may have selected different
archives or different event-live payloads between them.
